# Протокол агент ↔ панель, версия 1

Источник правды — [`src/index.ts`](src/index.ts) (zod-схемы). Go-типы в `agent/internal/proto`
повторяют их; фикстуры в [`fixtures/`](fixtures) разбирают тесты обеих сторон, поэтому расхождение
ломает CI, а не прод.

## Транспорт

- Агент сам открывает `wss://<панель>/ws/agent` (исходящее соединение, на мосту нет входящих портов).
- Заголовок апгрейда: `Authorization: Bearer <ключ ноды>`. Ключ выдаётся при регистрации и отзывается в панели.
- Кадры — текстовый JSON, один объект на кадр, поле `t` — тип сообщения. Лимит кадра 4 МБ.
- Панель шлёт WebSocket ping каждые 20 с. Агент переподключается с экспоненциальным backoff (1 с → 60 с, джиттер).

## Регистрация (HTTP)

`POST /api/agent/enroll` `{token, protocol, agentVersion, hostname}` → `{nodeId, key}`.
Токен одноразовый и живёт 24 часа. В панели хранится только SHA-256 токена и ключа.

## Рукопожатие и версия

1. Агент → `hello` (содержит `protocol`, версии, список поддерживаемых `ops`).
2. Панель проверяет `MIN_PROTOCOL_VERSION ≤ protocol ≤ PROTOCOL_VERSION`. Иначе закрывает соединение кодом `4000`.
3. Панель → `welcome` (`nodeId`, период метрик). Только после него агент шлёт `metrics`.

Добавление необязательных полей версию не меняет. Удаление, переименование или смена смысла — повышает `PROTOCOL_VERSION`.

## Сообщения

| Направление | `t` | Назначение |
|---|---|---|
| агент → панель | `hello` | рукопожатие |
| агент → панель | `metrics` | снимок раз в 15 с: система, `show stat`, `show table st_clients` |
| агент → панель | `result` | ответ на `cmd` (`id`, `ok`, `error`, `data`) |
| агент → панель | `checks` | результаты проверок «агент → выход»: TCP + TLS ClientHello с SNI маршрута |
| панель → агент | `welcome` | подтверждение, параметры |
| панель → агент | `cmd` | операция из фиксированного списка |
| панель → агент | `checks_config` | что проверять по расписанию (выход × SNI, признак PROXY v2); шлётся при подключении и при каждом изменении маршрутов |

Счётчики в `metrics` накопительные. Скорости считает панель по разнице соседних снимков
(сброс счётчика — значение меньше предыдущего — трактуется как рестарт, дельта = новое значение).

## Безопасность: фиксированный набор операций

Агент выполняет только `op` из закрытого перечня (`OPS`). Неизвестная операция отклоняется
ответом `unsupported_op`, аргументы валидируются на стороне агента. Произвольных команд, путей и
шеллов в протоколе нет и быть не должно: взлом панели не должен давать shell на мостах.

Операции версии 1 (список растёт без смены версии протокола: агент сообщает поддерживаемые в `hello.ops`, панель не шлёт лишнего):

| `op` | Что делает агент | Аргументы |
|---|---|---|
| `ping` | отвечает | — |
| `get_config` | присылает текущий `haproxy.cfg` и его SHA-256 | — |
| `apply_config` | проверка → атомарная замена → reload → ожидание нового процесса → при неудаче откат | `version`, `cfg`, `sniMap`, `validateOnly` (только текст; **пути и имена команд в аргументах не принимаются**) |
| `run_checks` | прогоняет проверки сейчас и возвращает результаты | — |
| `apply_bans` | приводит таблицу nftables `inet popug_bans` к переданному списку (полная синхронизация или дельта), обрывает conntrack забаненных | `full` (полная синхронизация или дельта), `ban[]` (`ip`, `ttlSec`), `unban[]` |
| `get_clients` | таблица `st_clients` целиком (IP, соединения, объёмы, скорости) для экрана «Клиенты» | — |
| `update_agent` | скачивает бинарник с панели, проверяет SHA-256 и подпись ed25519 закреплённым ключом, подменяет себя, перезапускается; сторож откатывает неудачный запуск | `version`, `sha256` (**URL и пути не принимаются**: адрес берётся из локального конфига) |

`apply_config` в деталях. Пути берутся из локального конфига агента (`/etc/haproxy/haproxy.cfg`, `/etc/haproxy/maps/sni.map`). Единственные команды,
которые агент способен запустить, — `haproxy -c`, `systemctl reload|restart|is-active haproxy` и `journalctl -u haproxy` (чтение журнала при неудаче).
Перед записью текст проходит denylist директив, дающих выполнение чужого кода (`program`, `external-check`, `lua-load*`, `ssl-engine`, `setenv`…);
тот же список проверяет панель, а совпадение двух реализаций держит общий файл `fixtures/config_policy.json`.
Ответ: `Result.data` — `ApplyResult` (`applied`, `rolledBack`, `rollbackFailed`, `sha256`, `output`, `durationMs`), в том числе при ошибке.

`apply_bans`: защищённые адреса (приватные, loopback, link-local, multicast, адреса интерфейсов самой ноды, адреса выходов) агент не банит и перечисляет в `rejected[]` ответа (`active` — сколько банов действует). Срок бана — таймаут элемента nftables-набора.
`update_agent`: подпись покрывает версию, архитектуру и SHA-256 бинарника, поэтому подпись одной версии нельзя применить к другой; понижение версии запрещено.
В `hello` добавлены необязательные `configSha256` (для детекта дрейфа конфига) и `updateReady` (на ноде закреплён ключ подписи).

Проверки: агент шлёт `checks` каждые `intervalSec` (по умолчанию 30 с) и сразу после получения нового `checks_config`. Для выходов с PROXY protocol
агент перед ClientHello отправляет заголовок PROXY v2 с командой LOCAL, как это делает HAProxy при health check.

## Коды закрытия

| Код | Причина |
|---|---|
| 4000 | несовместимая версия протокола |
| 4001 | не авторизован (нет или неверный ключ) |
| 4003 | ключ отозван |
| 4004 | вытеснен новым соединением той же ноды |
| 4005 | некорректный кадр |
